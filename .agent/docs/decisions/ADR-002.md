# ADR-002 — harness/src/templates/ is the upstream; root .agent/ is a consumer

**Date:** 2026-08-21
**Status:** Accepted

## Context

This repo holds three harness-shaped things: the harness CLI + its shipped templates
(`harness/src/templates/`), this dotfiles project's own harness install (`.agent/`), and
nested installs inside managed dotfiles (e.g. `dot_config/nvim/.agent/`). During the
mattpocock/skills cherry-pick, all skill improvements were made in root `.agent/` on the
assumption it was the upstream. A downstream project's `/harness-pull` (maprios) then
received none of them — `harness fetch` compares projects against `harness/src/templates/`
only.

## Decision

`harness/src/templates/` is the single upstream. Every harness improvement lands there
first, generalized (`{{PROJECT}}` placeholders, no dotfiles specifics), verified by the
harness test suite. Root `.agent/` is an ordinary consumer: it takes updates via
`/harness-pull` and carries only dotfiles-specific hardening plus main-repo-only skills
(e.g. harness-cherry-pick, marked "not shipped"). Nested dotfile harnesses are never
touched by harness work. A nested `.agent/` inside `harness/` was considered and rejected:
a fourth harness adds root-resolution ambiguity for zero gain over the routing rule.

## Consequences

- `.agent/AGENTS.md` carries the routing directive and layout section; agents route edits
  by it.
- Template and `.agent/` copies of a skill may legitimately diverge; ports adapt to each
  side's content rather than blind-copying.
- Root `.agent/` can lag templates (it does today: commit ledger flow, critique, init,
  dev-spec) — closed deliberately via `/harness-pull`, not implicitly.
