# ADR-001 — The system wall clock is the source of truth for "now"

**Date:** 2026-08-17
**Status:** Accepted — supersedes D02-2 (`pi-agent-base/.pi/agent-docs/specs/agent-harness/02-spec-naming.md`)

## Context

D02-2 required every harness-generated date to come from git — `spec new` used the HEAD commit date
(`git log -1 --format=%cs`), `harness log` preferred `headCommitIso()`, and `Date.now()` was
prohibited. The goal was reproducibility: two agents replaying the same repo state would produce
identical filenames.

In practice the rule inverted the intent:

- Every session was stranded on the previous commit's date until the day's first commit landed, so
  `harness log session-end` opened yesterday's entry and today's work was filed under the wrong day.
- `harness spec new` hard-failed with `HarnessError("no-date")` in a repo with no commits — exactly
  the moment a first spec is written.

Reproducibility was never actually delivered either: the commit date drifts the instant a commit is
made, so the "stable" input was only stable between commits.

## Decision

`resolveLogDate()` (`src/commands/log.ts`) and `specNew()` (`src/commands/spec.ts`) read the system
wall clock. An explicit `--date YYYY-MM-DD` still wins and remains the mechanism tests use to pin
dates. HEAD's commit time is no longer consulted anywhere; `headCommitIso` / `headCommitDate` are no
longer imported by either command, and the `no-date` error path is gone.

## Consequences

- A session logs under the day it happened; a spec created today is dated today.
- Determinism in tests comes from `--date`, not from git state — which is also how the existing
  tests were already written.
- Log/spec filenames are no longer reproducible from repo state alone. Accepted: these are diary and
  scaffold artifacts, committed once and never regenerated.
