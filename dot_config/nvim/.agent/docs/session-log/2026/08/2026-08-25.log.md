### Decisions made
- The 2026-08-17 fix is superseded, not wrong on its symptom: it correctly
  measured a ~1.1s stall and correctly located it in the markdown treesitter
  highlighter. It was wrong about the mechanism — it capped the highlighter by
  file size (1500 lines) instead of removing the specific query directive
  causing the cost, so it substituted Vim's regex `syntax/markdown.vim` above
  the threshold and ate that engine's limitations instead.
- Root cause: `$VIMRUNTIME/queries/markdown/highlights.scm` sets
  `(#set! conceal_lines "")` on the fenced-code delimiter and the info-string
  language label. Markdown is the only language in the runtime + installed
  plugin query set that uses `conceal_lines` (verified by grep), which is why
  markdown alone was pathological. That metadata sets `has_conceal_line` on
  the query, which sets `TSHighlighter._conceal_line`
  (`highlighter.lua:108-112`), which makes Nvim invoke the `on_conceal_line`
  decoration callback once per screen row; each call runs
  `tree:parse({row, row})` plus a full `prepare_highlight_states` walk of
  every injected child tree (`highlighter.lua:521-533`). The per-row memo
  `_conceal_checked` is cleared on every `on_bytes`, so the whole sweep is
  repaid after each keystroke. Fix: strip the directive from the query text at
  runtime instead of gating by size.
- Rejected: stripping `injection.combined` (forces a full-document injection
  scan on every re-resolution, `languagetree.lua:1102`) — measured, left the
  post-edit parse unchanged at ~19ms. Not worth the invasive query override.
- Kept `vim.g.markdown_fenced_languages` — it drives LSP hover-popup regex
  syntax, unrelated to the treesitter injection path it was originally
  (incorrectly) commented as controlling.
- Patch the query **globally** via `vim.treesitter.query.set`, not per buffer.
  A per-buffer variant was built and reverted: it started the highlighter with
  `vim.treesitter.highlighter.new(parser, { queries = { markdown = patched } })`
  for `buftype == ""` only, so scratch/float buffers kept upstream behaviour.
  Reverted because (a) its whole premise — that `conceal_lines` was collapsing
  fence rows in LSP hover floats — was disproved by a control run, and (b) it
  depended on `highlighter.new`'s semi-internal `opts.queries` and on winning
  an ordering race against whoever calls `vim.treesitter.start` first. The
  global form is public API, needs no ordering guarantee, and covers `mdx`
  (which resolves to the markdown parser, so it reads the same query) for free.
- `<leader>T` for the task toggle, not `<leader>tt`. The `<leader>t` prefix
  already carries six maps (`to`/`tf`/`tl`/`te` huez, `tc` ts-context, `tp`
  mini-pairs), so `tt` would pay a 500ms `timeoutlen` wait on every press —
  the exact pattern `standards/keymaps/leader-namespaces-and-collisions.md`
  warns against for `<leader>b`/`<leader>w`. A bare capital is one keystroke.
  Audited free against the global keymap table and the disabled specs that
  still hold capitals (`B`, `D`, `E`, `X`, `Z`, `Y`, `<S-w>`).
- Added `.chezmoiremove` at the chezmoi source root. Deleting a file from the
  source tree does NOT delete the target — chezmoi just stops managing the path
  and leaves the old copy loading. Without this the duplicate-injection cleanup
  would silently never take effect on any already-provisioned machine.

### Problems hit
- The symptom the developer actually reported this session — fenced-code
  highlighting dropping out partway down long markdown specs, in large
  contiguous sections — was the 2026-08-17 gate's own regex fallback failing,
  not a recurrence of the original stall. `syntax/markdown.vim` sets
  `syn sync minlines=50` (`g:markdown_minlines`, default 50): Vim's regex
  engine resolves at most 50 lines above the window top when no syntax state
  is cached, so it cannot tell it's inside a fenced block that opened further
  back. Reproduced on `.agent/docs/specs/2026-08-17-undo-guard/spec.md`
  (2179 lines, a `typescript` fence spanning lines 487-873) in the live
  pre-change config: `synstack()` returned `markdownHighlight_typescript` at
  line 500 and nothing at all at lines 700, 800, 870. `syntax sync fromstart`
  resolved every probe correctly, confirming the sync window as the cause. The
  fallback path had never been verified as a highlighting-equivalent
  substitute — only as a stall-avoidance measure.
- Built and reverted a per-buffer version of the query patch. It gated on
  `buftype == ""` and used `vim.treesitter.highlighter.new(parser, { queries =
  … })`, on the assumption that the global strip would regress LSP hover floats
  by un-collapsing their ``` rows. Two findings killed it: it left `mdx`
  buffers with `_conceal_line = true` (mdx.nvim starts its own highlighter
  after our FileType autocmd, so the patch lost the ordering race), and a
  control run — the same `vim.lsp.util.open_floating_preview` against the
  pre-change live config and the patched one — produced byte-identical screen
  output, fence markers visible in BOTH. Nvim's float path never applied
  `conceal_lines` to those buffers, so there was nothing to protect. Lesson:
  the control run should have come before the workaround, not after it.
- `chezmoi` auto-apply (chezmoi.nvim's apply-on-write) propagated every
  modification and the new `lua/util/markdown.lua`, but NOT the deletion of
  `after/queries/markdown/injections.scm` — the live copy was still being
  loaded, so the duplicate-injection cleanup had silently not taken effect.
  This is documented chezmoi behaviour, not a bug: dropping a file from source
  unmanages the path, it does not delete the target. Fixed by creating
  `.chezmoiremove` at the source root; `chezmoi status` now reports
  `D .config/nvim/after/queries/markdown/injections.scm` and a dry-run
  confirms the removal.
