# Commits — 08-18-2026

## 15:28

feat(nvim): protect undo history and coalesce barbar renders

**Undo history survives out-of-band edits.** Neovim binds an undofile to a SHA of the file's
contents, so a rewrite it never observed makes the stored tree unusable — silently discarded on the
next open, and unrecoverable (`:rundo` refuses it too). Measured: a file with three undo states
reopened at `seq_last=3` untouched, and `seq_last=0` after an out-of-band write. A file that *is*
loaded absorbs the same write as a new undo state via 'undoreload' and rewrites its undofile, so
history survives.

`lua/util/undo.lua` closes that gap from three directions. `M.hold` loads a file into a hidden,
unlisted buffer before something else rewrites it; agent tool-call hooks call it through
`scripts/undo-guard-notify.ts`, which speaks msgpack-RPC straight to the socket every nvim already
listens on via `v:servername` — no `serverstart`, and no `nvim --server` subprocess, which would
spend ~40ms starting a second nvim for a ~2ms round trip. `M.arm` additionally preloads every file
under the cwd whose undofile was touched in the last 7 days, covering what no hook can see: a
`git checkout`, `prettier --write .`, `npm install`, or codegen, none of which pass through a tool
call. `scripts/undo-guard-paths.ts` extracts the targets shell commands name outright (`sed -i`,
`tee`, `>`, `patch`, `mv`, `cp`), shared by the Claude Code `PreToolUse` and omp `tool_call` hooks.

`M.hold` only unlists, tracks or deletes a buffer it created — a harpoon pin or session restore
lists its files before loading them, and touching one drops it from the tabline or closes it
outright. Both kinds of buffer it loads get their filetype restored on first visit, since loading
under `eventignore=all` skips `BufReadPost`/`FileType` and nvim never delivers those later on its
own. Verdicts for files without usable history are cached per path, and the whole
create/inspect/delete window is event-suppressed, because leaking `BufWipeout` into barbar's state
on every historyless file cost 5617 tabline renders in one session.

This also replaces the previous `FileChangedShell`/`FileChangedShellPost` pair, which never fired on
unmodified buffers while its mere registration suppressed nvim's default action — swallowing the
`W12` conflict warning — with a `v:fcs_choice = "reload"` handler, and fixes the earlier inline
`:UndoGuardHold` leaking `eventignore = "all"` when `bufload` threw, which silently disabled every
autocmd for the rest of the session. Cost: ~29ms of chunked background work and +5.7MB RSS per nvim
process. Unwindowed was measured and rejected at 151ms/+25.4MB for one project, 385ms/+57.1MB for
another.

**Oil navigation is instant again.** Moving around the project in oil paused for ~100ms per
directory change, and with enough buffers open the editor became unusable. Profiling put the cost in
the tabline, not in oil: one 87ms oil stall sampled 96 times inside barbar's `get_unique_name`, and a
later run recorded 5617 `barbar render.update` calls at 4.31ms each — 24 seconds of CPU in a single
session — with 21 `DiagnosticChanged` events inside one 130ms window. The renders were invisible as a
tabline problem because the tabline always ended up correct; they just blocked oil from painting.

`get_unique_name` scanned every loaded buffer and called `vim.fn.fnamemodify` per iteration, once per
rendered tab, so cost grew as a session accumulated buffers. It now builds a basename map from one
memoised `getbufinfo({buflisted = 1})` call, takes basenames by pattern match, and memoises path
splits: 0.809ms to 0.074ms per render. Considering only listed buffers is also more correct, since
barbar cannot render an unlisted one. Labels were diffed old against new across seven buffer sets —
unique names, two- and four-way collisions, collisions two and three levels up, mixed depths and
dotfiles — and are byte-identical.

Every reactive render now goes through one `schedule_render` sharing a single reused timer handle,
and barbar's own pure-render autocmds are replaced with coalesced equivalents. That last part is what
made oil navigation slow: oil creates a new `oil://` buffer per directory, so `BufNew`, `BufEnter`,
`BufWinEnter` and `WinEnter` each fired a full render, one of them the variant that recomputes every
tab's label. `update_names` sticks across a coalesced burst so no label refresh is lost; interactive
events use a 16ms window because a render also repaints which tab is active, while diagnostics get
60ms. `VimResized` is deliberately left to barbar so resizes still repaint immediately, and its
`BufDelete`/`BufWipeout` handler is untouched because it also updates jump-mode letters and the
recently-closed list. `oil.toggle_float` went from 116ms avg / 139ms max to 11.8ms / 20.0ms — better
than the 18.2ms recorded baseline — with renders down to 787 calls and 4.2s of CPU, and zero stalls.

**Knowledge captured.** Two ADRs record both mechanisms with their measurements and rejected
alternatives; `standards/lua-style/autocmds.md` collects the five traps paid for here (augroup
`clear = true` deleting a sibling autocmd, bare `:checktime` skipping hidden buffers, `eventignore`
restoration, never mutating a buffer you did not create, and coalescing a plugin's pure-render
autocmds); `perf-baseline.md` carries the new healthy numbers so a future session does not diagnose
against the stale 18.2ms figure.
