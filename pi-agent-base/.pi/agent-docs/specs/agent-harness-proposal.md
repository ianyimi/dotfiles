## 1. Diagnosis — What's Wrong Today

### 1.1 Harness Staleness (Primary Pain)

The harness drifts because there's no mechanical enforcement:

- `developer-preferences.md` grows monotonically — 193 lines, no compaction — every spec runs against polluted context
- `tech-stack.md` has no `verified_at` field — agents trust it even after packages change
- `standards/index.yml` entries marked `"Needs description"` — index never rebuilt after adding files
- AGENTS.md references stale paths and port numbers
- Skills in one project never ported to another — no sync mechanism

Root cause: **updating the harness competes with shipping features.** Without a mechanical staleness signal, drift is the default.

### 1.2 Spec Quality Degradation

Global `dev-spec.md` is 345 lines. Project-local is 246. Both read whole every invocation. Two monotonic growth sources (new rules + learned preferences) with no decay. The model can't prioritize — everything has equal weight. Variable names in specs don't match developer conventions, causing rework on every implementation.

### 1.3 Platform Coupling

Everything is built for Pi. Claude Code sessions start from scratch. The fix is the wrong layer — mapping Pi concepts to Claude Code concepts requires two parallel systems. The right layer is bash + filesystem: every platform can run a command and read a file.

### 1.4 Context Loading Is Unreliable

Standards exist but agents don't consistently load them. It needs to be automatic (OMP file-pattern injection) or CLI-driven (`harness context`) — not a judgment call.

### 1.5 No Cascade Protocol

When requirements change, nothing identifies all downstream harness files that need updating. Agents fix the immediate file and miss the others.

## 2. Design Principles

1. **Platform-agnostic core.** Everything lives in `.agent/` as plain markdown. No platform syntax in the source of truth.
2. **Generated shims, not maintained.** `.pi/`, `.claude/`, `.omp/` are output artifacts from `harness sync`. Gitignored. Fix the source, re-sync.
3. **Mechanical over instructional.** Automated staleness checks beat "remember to update X."
4. **Rules only when corrected.** Don't preemptively write rules. Add a rule when the agent does something wrong. Keep AGENTS.md directives minimal — they load on every prompt.
5. **Skills loaded by relevance.** Skills inject only when relevant. The description is the key.
6. **Decay is a feature.** Preferences compact. Anti-patterns never auto-decay.
7. **Cascade changes are always surfaced.** When any harness file changes in a way that has downstream implications, the agent shows the complete change set to the developer for approval before applying any of it.
8. **The harness is self-building.** Init creates the harness. Doctor catches drift. Sync-spec feeds patterns back. The system improves with every session.
9. **Minimal context per invocation.** Skills are routers (≤150 lines). Content is in reference files loaded per-step.
10. **Determinism over trust.** The CLI handles all mechanical work — file creation, compaction, index rebuilding, shim generation, dep cloning.

### 3.2 Session Log vs Decisions — The Distinction

These are different things that serve different purposes. Combining them would make ADRs unsearchable.

| | `session-log/YYYY/MM/YYYY-MM-DD.log.md` | `decisions/ADR-NNN.md` |
|---|---|---|
| **Shape** | Diary entry — narrative, dated, append-only | Reference document — stable, indexed |
| **Question it answers** | "What happened that day? Why did we make X choice?" | "What is our current stance on X?" |
| **Growth** | Grows every session | Rarely changes once written |
| **How to read** | Chronologically to understand history | Directly by topic to get the current answer |
| **Superseded** | Never — it's a record | Yes — old ADRs are marked superseded |
| **Doctor checks** | No | Yes — doctor checks ADRs against tech-stack.md |

The session log is the story. Decisions are the index. A session log entry might say "we decided to use Better Auth" in passing. The ADR captures that decision permanently and is what the doctor checks for consistency.

### 3.3 Standards Domains Are Not Defaults

Standards folders are created by `harness init` based on what the project needs. The init interview determines which domains apply. **The agent never creates an empty standards folder.**

**`context-rules.yaml` is generated from active standards folders** by `harness sync`. When a domain folder is added, renamed, or deleted, `harness sync` regenerates the rules to match.

### 3.4 Naming Conventions + Directory Structure — Two Linked Files

These two files form a live, bidirectionally-linked pair and are among the most actively maintained files in the harness.

**The system is universal. The content is always project-specific.**

The format — a machine-readable YAML `rules:` block for file/folder names plus a descriptive section for code identifiers — is the same for every project. The content is completely different per project: a TypeScript monorepo has `react-components` and `convex-modules` rules; a Python automation project has `test-modules` and `page-object-classes` rules; a dotfiles repo has `chezmoi-templates` rules. `harness init` Phase 8 populates the content through interview + codebase inference. There are no default rules that apply to all projects.

**`standards/naming-conventions.md`** defines the rules — with regex patterns where applicable — for every naming context in the project: file names, folder names, variables, constants, functions, hooks, types, components, and any other project-specific constructs. It is the authoritative source of "what should this be called?"

**`standards/directory-structure.md`** shows those rules applied to the actual project tree. It is a live, annotated directory map — generated by `harness struct`, updated automatically whenever the project structure changes. Every folder annotation links back to the relevant rule ID in `naming-conventions.md`. Every folder added to the project appears here on the next `harness sync`.

**The linking contract:**
- `naming-conventions.md` contains: `See also: directory-structure.md — rules applied to the actual project layout`
- `directory-structure.md` contains: `See also: naming-conventions.md — full rule definitions and regex patterns`
- Every folder annotation in `directory-structure.md` cites `[→ rule-id]` referencing the rule in `naming-conventions.md`

**When they update:**

| Event | What updates |
|---|---|
| New file added to project | `directory-structure.md` (harness sync or harness struct) |
| New folder added | `directory-structure.md` + `context-rules.yaml` |
| Developer renames something from spec | `naming-conventions.md` (via sync-spec) |
| New naming pattern emerges | `naming-conventions.md` (via sync-spec) |
| Naming rule changes | `naming-conventions.md` + cascade check on `directory-structure.md` |

**Doctor checks both:** a new file that violates a regex rule in `naming-conventions.md` is flagged. A folder in `directory-structure.md` that no longer exists is flagged.

## 4. The CLI — `harness`

### 4.1 Why a CLI

Determinism. Every filesystem operation that can be made mechanical should be. The CLI handles file creation, preference compaction, index rebuilding, shim generation, dependency cloning, and doctor checks. This removes hallucination surface from these operations.

Platform parity. Every platform can run `harness` as a subprocess. OMP hooks, Pi skills, Claude Code hooks — all call the same CLI with identical behavior. Only the ergonomics differ.

### 4.2 Distribution — No Node/npm Required

**npm:**
```bash
npm install -g @zaye/harness
npx @zaye/harness init
```

**Standalone binary (no runtime needed):**
Built with Bun's `--compile` flag. Published to GitHub Releases on each version tag.
```bash
# macOS arm64
curl -L https://github.com/ianyimi/harness/releases/latest/download/harness-darwin-arm64 \
  -o /usr/local/bin/harness && chmod +x /usr/local/bin/harness

# Or via install script (detects platform automatically)
curl -sSf https://raw.githubusercontent.com/ianyimi/harness/main/install.sh | sh
```

The binary embeds default skill templates. On first run it extracts them to `~/.harness/`. Set `HARNESS_HOME` to override the extraction location. Copy the binary anywhere in PATH — it's fully self-contained.

### 4.3 Command Reference

**Setup:**
```bash
harness init                          # Hybrid init: infer + confirm, write .agent/
harness init --template <name>        # Init from a saved template (shorter interview)
harness sync                          # Regenerate .pi/, .claude/, .omp/ from .agent/
harness doctor                        # Check staleness, print actionable TODO
harness upgrade                       # Migrate templates against base package version
harness index rebuild                 # Regenerate docs/standards/index.yml
harness struct                        # Regenerate directory-structure.md from actual project tree
harness struct --check                # Check for naming violations only (no write)
```

**Dependency clones:**
```bash
harness deps clone                    # Clone all deps in manifest.json#dependencies
harness deps sync [<package>]         # Update clones to current pinned versions
harness deps add <package>            # Add dep to registry and clone it
harness deps remove <package>         # Remove dep from registry
harness deps list                     # Print dependencies/registry.md
```

**Spec + implementation:**
```bash
harness spec new "<slug>"             # Create spec.md + spec-tasks.md with frontmatter
harness spec list                     # List open specs from frontmatter
harness implement "<slug>"            # Run implementation agent loop on a spec
harness implement "<slug>" --from T3  # Resume from a specific task group
harness polish "<slug>"               # Run polish skill on completed spec (high-importance only)
```

**Session + state:**
```bash
harness state                         # Regenerate state.md
harness log append                    # Append to today's session log
harness log session-end               # Prompt "where I left off" → append to session log
harness context --for "<task>"        # Print relevant context files for this task
```

**Preferences + quality:**
```bash
harness pref compact                  # Compact preferences.md to budget
harness pref remove <id>              # Remove a specific preference (rollback)
harness env check                     # Verify all vars in env.manifest.md are set
harness worktree <feature>            # New worktree + tmux window (if applicable)
```

**Templates:**
```bash
harness template save <name>          # Save current .agent/ config as reusable template
harness template list                 # List saved templates
harness template inspect <name>       # Show what a template contains
harness template delete <name>        # Delete a saved template
```

## 6. Missing Harness Detection

If `harness init` has never been run, `.agent/` is empty or missing. Any agent that opens the project must detect this and stop — not attempt to answer questions with no context.

### The Minimal Committed Fallback

`.agent/AGENTS.md` is always committed, even before init:

```markdown
# [Project Name] — Agent Context

## ⚠️ Harness Not Initialized

`.agent/docs/` is empty. The agent harness has not been set up.

Run `harness init` before doing anything else. This will analyze the codebase,
ask targeted questions, and generate standards, skills, context rules, and
platform bridges for OMP, Pi, and Claude Code. Takes ~10–15 minutes.

After init, reload this file — it will be replaced with full project context.

Install: `npm install -g @zaye/harness`
Without npm: https://github.com/ianyimi/harness/releases/latest
```

### Detection Logic in Every Skill

Every SKILL.md starts with a 3-line preflight before any other step:

```
Preflight:
1. Does .agent/manifest.json exist? No → stop, tell user to run harness init.
2. Run harness doctor. Fix errors before proceeding.
3. Run harness state. Read the output.
```

## 7. Project Init — `harness init`

### Philosophy: Infer → Confirm → Write Immediately

The agent infers from the codebase, presents a draft per phase, developer confirms or corrects. Each phase is written immediately after confirmation — not accumulated at the end. Progress survives context compaction via `.agent/.setup-progress.md`.

### The Phases

**Phase 0: Existing harness check**
If `manifest.json` already exists: ask "Re-init (full rebuild) or update (specific sections)?" Update mode jumps only to the phases that need updating.

**Phase 1: Project Identity**
Scan manifest files (package.json, Cargo.toml, go.mod, pyproject.toml, Makefile, etc.). Detect language, ecosystem, repo structure. Infer project name. Present and confirm.
→ Write: `.agent/.setup-progress.md`

**Phase 2: Project Purpose + Team**
Ask: What does this project do? Who works on it (solo / small team / open source)? Is it a product, tool, automation, library? Determines: workflow tier default, project management depth, multi-engineer context keeping.

**Phase 3: Domains + Standards Folders**
Based on Phase 1+2, propose which domains apply. Never propose a domain the project doesn't need.

```
Based on your project, I'd create these standards domains:
  ✅ automation/  — browser automation patterns (Stagehand)
  ✅ ai/          — LLM prompt design and model selection
  ✅ testing/     — automation task test structure
  ❌ frontend/    — no UI
  ❌ backend/     — no server

Correct this list before I create the folders.
```

→ Write: domain folders with starter templates from `~/.harness/templates/standards/<domain>/`

**Phase 4: Tech Stack**
Parse dependencies from manifest files. Present detected stack. Ask about ambiguous choices.
→ Write: `.agent/docs/product/tech-stack.md` with `verified_at: <current-git-sha>`

**Phase 5: Dev Processes + Environment**
Detect scripts from package.json / Makefile. Ask: ports, tmux session/panes, verification commands. Ask: which env vars are required?
→ Write: `.agent/docs/product/dev-processes.md`, `.agent/env.manifest.md`

**Phase 6: Key Dependencies for Source Cloning**
Present top dependencies from manifest files. Ask which are open source and worth cloning. Recommend based on how deeply the project integrates with them.
→ Write: `manifest.json#dependencies`, `.agent/dependencies/registry.md`
→ Run: `harness deps clone`

**Phase 7: Workflow Tier + Importance + Active Modules**
Ask: developer implements all code (high-care) or agent implements directly (low-care)?
Ask: is this a high-importance project? (enables polish skill after implementation)
Propose modules based on project type.
→ Write: completes `manifest.json`

**Phase 8: Naming Conventions (High-Care Projects)**
For high-care projects: ask the developer to describe their naming preferences for:
- Hooks: `useXxx` / `useXxxState` / `useXxxMutation` pattern?
- Event handlers: `onXxx` / `handleXxx`?
- Booleans: `isXxx` / `hasXxx` / `shouldXxx`?
- Components: `XxxPanel` / `XxxSection` / `XxxContainer` / no suffix?
- Types: `XxxType` / `XxxT` / just `Xxx`?
- Any project-specific patterns (e.g. Convex query function naming)

Also analyze any existing code to infer patterns before asking — only ask about what can't be inferred.
→ Write: `.agent/docs/standards/naming-conventions.md`

**Phase 9: Mission + Roadmap**
Ask: what is the mission in one paragraph? What are the next 3 milestones?
→ Write: `.agent/docs/product/mission.md`, `.agent/docs/product/roadmap.md` (if enabled)

**Phase 10: Generate + Sync**
Run `harness sync` → generate `.pi/`, `.claude/`, `.omp/` shims.
Run `harness index rebuild` → generate `standards/index.yml`.
Run `harness state` → generate initial `state.md`.
Print: what was created, what the developer can delete from any old harness, how to install the CLI on other machines.
→ Delete `.agent/.setup-progress.md`

## 8. Init Templates

### What a Template Is

A template is a snapshot of a successful `harness init` configuration. It pre-answers all structural questions so future projects of the same type only need to answer project-specific questions (name, description, specific deps). Init with a template completes in ~3 min instead of 15.

### Saving + Using

```bash
harness template save convex-next-fullstack
# Saves: manifest structure (minus project-specific fields), standards domains,
#        skill overrides, dep registry pattern (names not versions — resolved fresh)
# To: ~/.harness/templates/convex-next-fullstack/

harness init --template convex-next-fullstack
# Skips: domain selection, tech stack detection, module selection, dep list
# Still asks: project name, description, team, mission, env vars, ports, naming conventions
```

### Built-in Templates (shipped with the CLI)

| Template | Stack |
|---|---|
| `convex-next-fullstack` | Convex + Next.js + TanStack + Tailwind 4 + Better Auth + pnpm monorepo |
| `next-api` | Next.js App Router + Prisma/Drizzle + tRPC |
| `node-cli` | Node.js CLI + oclif/yargs + Vitest |
| `python-automation` | Python + Playwright/Stagehand + pytest |
| `dotfiles` | Shell scripts + chezmoi + no domain standards |
| `library-ts` | TypeScript library + tsup + Vitest + Changesets |
| `astro-site` | Astro + content collections + Tailwind |

## 9. Dependency Source Clones

### Why

When writing a spec that deeply integrates with a library, the agent currently relies on web docs or training data — both can be wrong or outdated. The actual source at the exact pinned version is always correct.

### How It Works

During `harness init` Phase 6, the agent identifies key open-source deps and clones them into `.agent/dependencies/` at the version pinned in the project's manifest.

```
.agent/
└── dependencies/
    ├── .gitignore       ← "*" — entire folder gitignored
    ├── registry.md      ← COMMITTED — lists what's cloned and at what version
    ├── convex/          ← git clone at v1.17.4
    ├── better-auth/     ← git clone at v1.4.9
    └── tanstack-form/   ← git clone at v0.43.0
```

### Usage in Skills

Every skill that could benefit checks `registry.md` during the codebase exploration step:

```
1. Check .agent/dependencies/registry.md — which deps are cloned?
2. If writing a spec that extends a cloned dep, read relevant source files
3. Note actual function signatures and patterns — not docs, not training data
```

Particularly valuable for: accurate type stubs when extending a library, internal API usage, understanding hooks/lifecycle at the exact pinned version, debugging "is this a library bug or my code?"

### Doctor Check

```json
{
  "id": "stale-dependencies",
  "description": "Cloned dep versions don't match current pinned versions in package.json",
  "action": "harness deps sync",
  "severity": "info"
}
```

## 10. Knowledge Graph — How the Harness Learns

### The Protocol

The harness is a living knowledge graph. Every session that produces new knowledge triggers a write to the right file.

| New knowledge | Where it goes |
|---|---|
| Agent did something wrong (corrected) | `anti-patterns.md` + correction count |
| Developer changed code from spec pattern | `preferences.md` via sync-spec |
| Developer used a different naming convention | `naming-conventions.md` via sync-spec |
| New library/tool adopted | New standards file in domain folder |
| Architectural decision made | `decisions/ADR-NNN.md` |
| Discovered how a dep works | `research/` note OR domain standards file |
| New env var added | `env.manifest.md` |
| New file/folder added to project | `directory-structure.md` (harness struct) |
| New naming pattern observed | `naming-conventions.md` (sync-spec) |
| Session ended | `session-log/YYYY/MM/YYYY-MM-DD.log.md` |

Knowledge goes to the file — not the conversation, not the spec.

### Naming Conventions — How They're Learned

`naming-conventions.md` is initialized during `harness init` Phase 8 via a short interview + codebase inference and updated by sync-spec every time the developer changes a name from what the spec generated. It covers every naming context in the project and includes **machine-readable regex rules** for file and folder names that `harness struct --check` and `harness doctor` can validate automatically.

The file is always loaded during dev-spec step 2 for high-care projects and auto-injects via `context-rules.yaml` for any code file edit.

`directory-structure.md` is the live companion — generated by `harness struct`, updated by `harness sync` on any structural change, annotated with which naming rule applies to each path.

### Cascade Detection

When any harness file changes in a way that affects others, the agent identifies all downstream impacts and presents a single confirmation before applying any of them.

| Change | Files to check |
|---|---|
| Function/type renamed | All spec files with `touches` overlapping the changed path |
| New package added to monorepo | `tech-stack.md`, `dev-processes.md`, `context-rules.yaml` |
| New env var added | `env.manifest.md` |
| Decision superseded | `tech-stack.md`, any spec referencing the old decision |
| Standards domain renamed/deleted | `context-rules.yaml`, `index.yml`, specs citing that standard |
| Naming convention changed | `naming-conventions.md`, any open spec |
| Dep version upgraded | `registry.md`, prompt `harness deps sync` |

```
This change has downstream impacts. Confirm this full set before I apply anything:

1. Rename useTextfield() → useTextField() in packages/react/src/
2. Update 2 spec files: collections-ui/spec.md (line 47), field-types/spec.md (line 112)

## 11. Dev-Spec Workflow

### Overview

Redesigned around: quality throughout the full spec (subagent loop), build order that produces visible results early, LSP cleanliness at every step, naming conventions used from the start.

### Steps

**Preflight:**
```bash
harness doctor && harness state
harness context --for "<feature being specced>"
```

**1. Interview**
Load `references/interview.md`. Run Phase 1-3 questions. `ask_user_question` in OMP/Pi, plain numbered list in Claude Code.

**2. Explore Codebase**
Browse relevant packages. Check `dependencies/registry.md` — read dep source if relevant.
Read **in this order**:
1. `naming-conventions.md` (high-care) — before writing any code in the spec
2. `anti-patterns.md`
3. `preferences.md`
4. Domain standards files returned by `harness context`

Summarize findings. Note existing patterns to mirror.

**3. Surface Edge Cases**
Present design questions, edge cases, scope check. Confirm in/out before writing.

**4. Determine Build Order**
Load `references/build-order.md`. Order must satisfy:
- **Environment first** — config, package scaffolding, tooling. After this step, `build` and `test` run clean.
- **Visual feedback early** — stubs before internals. Developer sees something in browser/terminal by step 2 at the latest.
- **LSP-clean at every step** — if file A imports from file B, B's step comes before A's. Mutually-importing files appear in the same step with a note to create them together.
- **Test infrastructure before test files** — runner config and utilities before any `.test.ts` files.
- **Tests colocated with implementation** — `foo.test.ts` in the same step as `foo.ts`. Never pooled at end.
- **Dependencies before dependents** — utilities before orchestration.

**5. Create `spec-tasks.md`**
Run `harness spec new "<slug>"`. Write `spec-tasks.md` — ordered task groups with `Why:` and `Verify:` for each. Show to developer, confirm, update `tasks.md`.

> Developer can stop here: "just the tasks, I'll spec later." Stop and wait.

**6. Write `spec.md`**
Load `references/spec-format.md` and `references/code-rules.md`. **All names in spec code must follow `naming-conventions.md`.** This is verified before presenting the spec.

- **Short spec** (≤3 task groups, estimated ≤200 lines): write in one pass.
- **Long spec** (>3 task groups or estimated >200 lines): **subagent loop.**

Subagent loop — for each task group `Tn`:
```
Subagent input:
  - Project purpose: one line (manifest.json#description)
  - spec-tasks.md in full (titles + why + verify, no code — stays lightweight)
  - "Your job: write the spec section for T<N>: <title>"
  - Output of: harness context --for "<task group topic>"
  - naming-conventions.md (always)
  - anti-patterns.md (always)
  - Instruction: explore codebase for patterns in this domain before writing

Subagent output:
  - That spec section with all names following naming-conventions.md
```

Main agent stitches sections, reviews for consistency and naming, fills in cross-references.

**7. Naming Pass**
After writing (or stitching) the full spec: scan all variable names, function names, and type names against `naming-conventions.md`. Fix any that don't match before presenting to the developer. This is a final check — not a separate step the developer sees, just something the agent does before showing the result.

**8. Review Build Order**
Can developer run `build` + `test` after each step? Every step tagged `[dev]`/`[agent]`? Files in each step in declaration-before-consumer order?

**9. Present + Update Tasks**
Show: spec path, what's agent-generated vs dev-implemented, build order summary, estimated time per task group. Move task to "In Progress" in `tasks.md`.

## 12. Commit + Session Log

### What the Session Log Is

`session-log/YYYY/MM/YYYY-MM-DD.log.md` is an append-only chronological diary of what happened during development. It is **not** a decision index (that's `decisions/`). It is the story — what was built, what problems were hit, what was decided in the moment and why, where the session left off.

It gives future agents (and the developer) the ability to answer: "What was happening in early May? Why does this code look this way? What was the context for this decision?" without searching through git history.

### Structure of a Log Entry

```markdown
## 2026-08-02 — 14:23 — Collections UI Step 4 (filter panel)

**Spec:** docs/specs/2026-07-12-collections-ui/spec.md (Step 4)
**Commit:** (filled in after /commit)

### What was built
- `FilterPanel.tsx` — filter panel component wired to TanStack Table
- `useFilterState.ts` — hook managing filter state in URL params via nuqs

### Decisions made
- Used nuqs for filter state instead of useState — URL-shareable filters felt important
  for the admin use case. Not in the spec but low-risk addition.
- Kept FilterPanel as a controlled component (caller owns state) for flexibility.

### Problems hit
- nuqs `parseAsArrayOf` wasn't exported from the v2 package — used `parseAsJson` instead.
  This is a nuqs v2 quirk, not a bug in our code.

### Where I left off
Empty state test failing: expects 0 rows, gets 1 (header counted by selector).
Fix the test selector, not the component. Resume from this test fix.
```

### The Commit Skill

The commit skill is the endpoint of any work session. It **does not run `git commit`** — the developer does that manually (via lazygit or otherwise). The skill generates the commit message and ensures all project documents are current before the developer commits.

1. **Checks for today's log entry.** If `YYYY-MM-DD.log.md` doesn't exist or has no content beyond the header, prompt to fill it in:
   - What was built?
   - Any decisions that deviated from the spec?
   - Any problems hit and how they were resolved?
   - Where is the session leaving off?

2. **Generates the commit message.** Derived from the log entry — the headline becomes the commit title, "what was built" informs the body. Format: `type(scope): description` under 72 chars. Body explains why, not which files changed. Writes to `session-log/YYYY/MM/YYYY-MM-DD.commit.md`. Developer copies it when running lazygit.

3. **Updates project documents** based on what modules are active in `manifest.json`:
   - `docs/product/roadmap.md` — if milestone tasks were completed, tick them off
   - Engineering docs (e.g. `apps/docs/src/content/`) — if the build changed a public API, flag docs that need updating (don't rewrite docs automatically — present the list for developer review)
   - `tasks.md` — move completed tasks to "Recently Done"
   - `state.md` — regenerate via `harness state`
   - `decisions/` — if a new architectural decision was made and not yet recorded, prompt to write an ADR
   - `naming-conventions.md` / `directory-structure.md` — if new files were added, run `harness struct` to update the structure map

   Each document update is presented to the developer as a summary: "I updated these 3 files. The following need your attention: [list]." Nothing is silently changed.

4. **Presents the commit message** ready to copy. Developer stages in lazygit and pastes.

### Commit ↔ Sync-Spec Relationship

For high-care projects: **sync-spec runs before commit.** Sync-spec extracts patterns, updates preferences/naming-conventions, and writes the log entry. Commit then handles document updates and message generation.

For low-care projects: the implementation agent writes the log entry automatically after each task group. Commit can run directly.

```markdown

  a work session. Does NOT run git commit — developer does that manually via lazygit.

---

## Steps
1. Check today's session log. Missing or empty → prompt to fill in.
2. Write commit message → session-log/YYYY/MM/YYYY-MM-DD.commit.md.

3. Update project documents (check manifest.json#modules for what's active):

## 13. Implementation Agent

### When to Use

For **low-care projects** or specific specs where the developer wants the agent to write all the code. The developer reviews output at step boundaries and at the end, rather than implementing each step themselves.

### The Loop

```bash
harness implement "<slug>"            # run from first unchecked task group
harness implement "<slug>" --from T3  # resume from specific task group
```

For each unchecked task group in `spec-tasks.md`:

```
1. Read the spec section for this task group
2. harness context --for "<task group>" + check registry.md for dep source
3. Read naming-conventions.md (always)
4. Explore current codebase state (especially files from prior task groups)
5. Implement all steps in this task group, in order, following spec exactly
6. Run the task group's Verify command
   → Passes: mark complete in spec-tasks.md, write log entry, continue
   → Fails: attempt fix (max 2 retries), then pause and report to developer
7. Continue to next unchecked task group
```

### Rules

- Never deviate from the spec without asking
- Never skip a `[dev]` step — stop, tell developer what to implement, wait for confirmation
- Never continue past a failed verification without developer approval
- `verify: manual` steps always pause for developer confirmation
- All names in written code follow `naming-conventions.md`

### Verification Is Mandatory

Every task group in `spec-tasks.md` must have a `Verify:` line. In rare cases where no automated verification is possible, mark `verify: manual` — the implementation agent will pause and wait.

### Platform Notes

**OMP**: each task group is a separate subagent with full context budget.
**Pi / Claude Code**: task groups run serially; agent re-reads state and current task group section between groups rather than keeping everything in memory.

## 14. Polish Skill

### What It Is

A deep code review for **high-importance projects** after a spec has been implemented. It is not a style review — it's a semantic audit that asks: is the code actually correct and complete?

Enabled only when `manifest.json#workflow.importance === "high"`. Can be run manually (`harness polish "<slug>"`) or triggered automatically after `harness implement` completes.

### What It Checks

Load `references/polish-checklist.md`. The checklist covers:

**Error handling completeness:**
- Every async operation has a catch/error boundary
- Network errors are handled gracefully (not silently swallowed)
- Invalid input produces a clear user-facing error, not a crash
- Loading and empty states are explicitly handled (not just the happy path)

**Codepath coverage:**
- What happens when a list is empty?
- What happens when a required resource is missing or deleted?
- What happens when the user has no permissions?
- What happens when two users act on the same resource simultaneously?

**Edge cases from the spec:**
- Were all edge cases listed in the spec's "Edge cases" section actually implemented?
- Are there any `throw new Error("Not implemented")` stubs still in the code?

**Suggested improvements (lightweight only):**
The agent may suggest small, low-risk improvements that would improve UX without architectural changes. These are suggestions only — presented as a list, never applied without developer approval:
- A missing loading indicator on a slow operation
- A keyboard shortcut that would be natural given the UI
- An error message that could be more informative
- A missing confirmation dialog before a destructive action

The agent does **not** suggest new features, architectural changes, or anything requiring a new spec. Those go to `tasks.md` inbox if they're worth pursuing.

### Output

```
Polish complete for spec: collections-ui

## Error Handling
✅ FilterPanel — empty state handled
✅ Upload failures — toast notification shown
⚠️  BulkDeleteButton — no confirmation dialog before deletion of >1 item
    → Suggest: add AlertDialog (shadcn installed) before batch delete

## Codepath Coverage
✅ Empty collection — renders "No items" state
✅ Missing collection — 404 redirect handled in loader
⚠️  Concurrent edit — no conflict detection on save
    → Spec did not cover this. Add to tasks.md inbox?

## Spec Edge Cases
✅ All 3 edge cases from spec implemented

## Suggestions (your call, no action taken)
- [ ] Add keyboard shortcut Cmd+K to open filter panel (natural given Command palette)
- [ ] "No items match your filters" empty state is more specific than "No items"

2 warnings. 2 suggestions. No blocking issues.
Add warnings to tasks.md inbox? (yes / no)
```

## 16. Debug Skill

Always starts with git history analysis. Most bugs are introduced by a recent commit — this step is lightweight and high-signal.

### Protocol — First Steps, Always

```bash
git log --oneline -20                        # what changed recently
git diff HEAD~3..HEAD                        # what those commits actually changed
git log --oneline origin/dev..HEAD           # changes since last known-good dev branch
git log --oneline origin/master..HEAD        # changes since master
git stash list                               # any stashed work that might interact
```

If user says "it worked before X":
```bash
git log --oneline <branch>..HEAD             # all commits since it worked
git diff <branch>..HEAD -- <affected file>   # targeted diff on the specific file
```

Also check `session-log/` for the most recent log entry — the entry for the day the bug was likely introduced often describes the decision that caused it. And check `directory-structure.md` — if the bug involves a missing import or wrong path, the structure map shows where things actually live.

Then load `references/debug-hierarchy.md` — project-specific fragile areas.

## 17. General Agent Behavior

The generated `AGENTS.md` includes a directives section — under 20 lines — at the top. Keep it minimal. Only add directives when demonstrated to be needed.

### Subagent Auto-Routing

Within a single session the developer may switch context without switching tools — e.g. asking a debug question mid-spec, or asking for a commit after implementing. The harness handles this through **intent classification at message start**.

Every platform bridge generated by `harness sync` includes a routing directive that fires before any skill:

```
At the start of every message, classify the intent:
  - "I need to debug / something is broken / this isn't working" → load debug/SKILL.md
  - "write a spec / spec out X / what should we build" → load dev-spec/SKILL.md
  - "implement / build this / run the spec" → load implement/SKILL.md
  - "commit / generate commit message / end of session" → load commit/SKILL.md
  - "sync spec / update the spec / extract patterns" → load sync-spec/SKILL.md
  - "polish / review the code / check for completeness" → load polish/SKILL.md
  - "research / learn about / how does X work" → load research/SKILL.md or learn/SKILL.md
  - General project question → read state.md, answer from harness context

If ambiguous, proceed with current skill but note the classification at top of response.
```

**In OMP**: this becomes native subagent routing — each intent maps to a named subagent defined in `.omp/agents.yaml`. Switching agents within a session is handled by the platform. Each agent carries only the context relevant to its skill, so the model gets full context budget for the new task.

**In Pi**: skill trigger descriptions already handle most of this — each skill's `description` frontmatter includes the trigger phrases above, so the right skill fires automatically.

**In Claude Code**: the routing directive lives in `.claude/CLAUDE.md` as a plain instruction. The model classifies and loads the right skill manually at the start of each response.

This means a developer can stay in one session, ask a debug question after writing a spec, and get a debug-quality response — the harness routes it to the right context and skill without requiring a new session.

### AGENTS.md Directives Block

```markdown
## Agent Directives

These apply to all agents, all platforms, always.

**Route by intent.** At the start of every message, classify what the user needs
(debug / spec / implement / commit / general) and load the appropriate skill.
See .agent/skills/ for the full skill list and their trigger conditions.

**Ask before large actions.** If a request is ambiguous or would affect multiple
files in unspecified ways, ask one clarifying question before proceeding.

**Surface cascade impacts before writing.** When a change has downstream effects
on other harness files, show the complete change set to the developer for approval
before applying any of it.

**Detect missing harness.** If .agent/docs/ is empty or manifest.json is missing,
stop and tell the user to run harness init.

**Doctor first.** On session start, run harness doctor. Fix errors before starting.

**Write knowledge to the graph.** Corrections → anti-patterns.md. Patterns →
preferences.md. Naming → naming-conventions.md. Structure → harness struct.
Decisions → decisions/. Sessions → session-log/.
```

**What does NOT go here:** technology rules, anti-patterns, process rules, library usage rules. Those go in the relevant standards file or skill reference, loaded only when relevant.

# ADR-001: Better Auth over NextAuth

## Decision
Use Better Auth with the Convex adapter, pinned `>=1.4.9 <1.5.0`.

## Context
VexCMS needs auth that works natively with Convex's reactive data model.
NextAuth requires REST-style polling — no first-class Convex adapter.

## Reason
Better Auth's session model maps directly onto Convex documents.
The `@convex-dev/better-auth` adapter gives real-time session invalidation without polling.

## Consequences
- Pinned version range until Better Auth API stabilizes past 1.5.0
- Must monitor Better Auth releases for breaking changes
- `@vexcms/better-auth` handles the adapter — don't import Better Auth directly in app code

## Checked Against tech-stack.md
2026-08-02 — consistent ✅

```yaml
rules:
  # ── File naming ────────────────────────────────────────────────────────────
  - id: react-components
    pattern: "^[A-Z][a-zA-Z0-9]+\\.tsx$"
    scope:
      - "packages/react/src/components/**"
      - "apps/www/src/components/**"
    description: React components — PascalCase .tsx
    examples: ["FilterPanel.tsx", "CollectionTable.tsx"]
    counter_examples: ["filterPanel.tsx", "filter-panel.tsx", "FilterPanel.ts"]

  - id: react-hooks
    pattern: "^use[A-Z][a-zA-Z0-9]+\\.ts$"
    scope: ["**/hooks/**"]
    description: React hooks — camelCase with use prefix, .ts extension
    examples: ["useFilterState.ts", "useCollectionMutation.ts"]
    counter_examples: ["FilterState.ts", "useFilterState.tsx"]

  - id: convex-modules
    pattern: "^[a-z][a-zA-Z0-9]+\\.ts$"
    scope: ["convex/**"]
    description: Convex function modules — camelCase .ts
    examples: ["collections.ts", "fieldTypes.ts"]
    counter_examples: ["Collections.ts", "field-types.ts"]

  - id: test-files
    pattern: "^.+\\.test\\.tsx?$"
    scope: ["**"]
    description: Test files — source name + .test.ts or .test.tsx
    examples: ["FilterPanel.test.tsx", "useFilterState.test.ts"]
    counter_examples: ["FilterPanel.spec.tsx", "FilterPanelTests.ts"]

  - id: type-files
    pattern: "^types\\.ts$"
    scope: ["packages/*/src/**"]
    description: Type definition files — always named types.ts, colocated with config.ts
    examples: ["types.ts"]
    counter_examples: ["Types.ts", "fieldTypes.ts", "interfaces.ts"]

  # ── Folder naming ──────────────────────────────────────────────────────────
  - id: spec-folders
    pattern: "^\\d{4}-\\d{2}-\\d{2}-[a-z][a-z0-9-]+$"
    scope: [".agent/docs/specs/*/"]
    description: Spec folders — YYYY-MM-DD-kebab-slug
    examples: ["2026-08-02-richtext-image-uploads"]
    counter_examples: ["richtext-image-uploads", "2026-08-02_richtext"]

  - id: standards-domains
    pattern: "^[a-z][a-z0-9-]+$"
    scope: [".agent/docs/standards/*/"]
    description: Standards domain folders — lowercase kebab-case
    examples: ["backend", "frontend", "browser-automation"]

  - id: session-log-structure
    pattern: "^\\d{4}$"
    scope: [".agent/docs/session-log/*/"]
    description: Session log year folders — 4-digit year only

## Code Identifier Conventions

*(Descriptive — enforced during spec naming pass and sync-spec review)*

### Hooks
- Data access: `useXxx()` returns data directly — not `useXxxData()` or `useXxxQuery()`
- Mutations: `useXxxMutation()` returns `{ mutate, isPending }`
- Context access: `useXxx()` matches the context name, no suffix

### Components
- Panels/sections: no container suffix — `FilterPanel`, not `FilterPanelContainer`
- Pages: `XxxPage` suffix always
- Layouts: `XxxLayout` suffix always

### Event Handlers
- Inline props: `onXxx` — `onChange`, `onSubmit`, `onDelete`
- Internal methods: `handleXxx` — `handleFilterChange`, `handleBulkDelete`

### Booleans
- State flags: `isXxx` — `isLoading`, `isEmpty`, `isOpen`
- Capabilities: `canXxx` — `canEdit`, `canDelete`
- Avoid `hasXxx` for state (reserved for existence checks: `hasPermission`)

### Constants
- Exported module constants: `SCREAMING_SNAKE_CASE` — `ADMIN_FIELDS`, `MAX_RETRY_COUNT`
- File-local constants: `camelCase` — `defaultPageSize`, `fallbackRoute`
- Enum-like objects: `SCREAMING_SNAKE_CASE` keys — `{ TEXT: "text", NUMBER: "number" }`

### Convex Functions
- Queries: `get` (single by id) / `list` (collection) — `getCollection`, `listCollections`
- Mutations: `create` / `update` / `delete` — never `insert`, `save`, `remove`, `upsert`
- Actions: `run` prefix — `runIndexing`, `runExport`

### Types
- External/input types: `XxxInput` — `CollectionInput`, `FieldConfigInput`
- Internal/resolved: just `Xxx` — `Collection`, `FieldConfig`
- Never: `XxxType`, `XxxT`, `IXxx`, `XxxModel`

### Props Objects
- Parameter name is always `props` — never `opts`, `args`, `options`, `config`
- Destructure only when the function body has no locally-defined variables

### 18.7 `dev-spec/SKILL.md` — Slimmed Router

```markdown
---
name: dev-spec
description: Use BEFORE any non-trivial code change — new features, adapters, API changes,
  anything touching multiple files. Triggers on "write a spec", "spec out X", "/dev-spec",
  or when the agent recognizes the work is substantial. Skip for typos, single-line tweaks.
model_tier: frontier
---

# Dev Spec

## Preflight
```bash
harness doctor && harness state
harness context --for "<feature being specced>"
```

## Steps
1. **Interview** — load references/interview.md. Phase 1-3 questions.
2. **Explore** — check registry.md for dep source, read naming-conventions.md
   (always, first), anti-patterns.md, preferences.md, domain standards.
3. **Edge cases** — surface design questions + scope check. Confirm in/out.
4. **Build order** — load references/build-order.md. Environment-first,
   visual-early, LSP-clean, tests colocated.
5. **spec-tasks.md** — `harness spec new "<slug>"`. Task groups + why + verify.
   Show developer. → Stop here if requested, or continue.
6. **spec.md** — load references/spec-format.md + references/code-rules.md.
   Short (≤3 groups): one pass. Long (>3): subagent loop, one per group.
   All names must match naming-conventions.md. Run naming pass before presenting.
7. **Review build order** — build+test runnable after each step?
8. **Update tasks** — move to In Progress. Present summary.

Platform: ask_user_question → plain list in Claude Code.
```

### 18.8 `commit/SKILL.md`

```markdown
---
name: commit
description: Stage and commit current changes. Triggers on "commit", "/commit",
  "git commit", or naturally at end of a work session. Always checks for a session
  log entry before committing. For high-care projects, sync-spec should run first.
model_tier: cheap
---

# Commit

## Preflight
Check: does today's session-log/YYYY/MM/YYYY-MM-DD.log.md exist and have content?
If not: prompt for what was built, decisions made, problems hit, where left off.

## Steps
1. **Log check** — ensure today's session log is written (above).
2. **Stage** — show diff summary. Ask developer to confirm what's staged.
3. **Commit message** — derive from session log. Load references/session-log-format.md.
   Title: `type(scope): description` under 72 chars.
   Body: what was built and why (from log). Deviations from spec.
4. **Commit** — run git commit.
5. **Backfill** — append commit SHA to today's log entry (Commit: field).
6. **State** — run harness state. Mark tasks complete if spec is done.
```
