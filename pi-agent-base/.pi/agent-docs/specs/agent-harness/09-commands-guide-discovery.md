> Phase spec 9 (added 2026-08-07 after developer review of the built 01–04 surface). Prereqs:

## Overview

Three developer-experience gaps closed:

1. **Explicit slash commands on every platform.** Skills become first-class `/dev-spec`,
   `/sync-spec`, `/commit`, … via generated command shims — identical, deterministic invocation
   instead of platform-dependent skill triggering. Init is `/harness-init` on Claude Code
   (builtin `/init` collision) and `/init` on OMP.
2. **`docs/harness-guide.md`** — a per-project explanation of how THIS harness is organized:
   where each kind of knowledge goes, how the code map links (`applies_to` → context-rules.yaml
   → `harness context`/instructions), what is generated vs authored, and the budgets. Written by
   `init finish`; the doc future agents read before editing the harness.
3. **The init discovery pass.** After interview phases 1–9 and before `finish`, the init skill
   sweeps the ENTIRE codebase domain by domain and writes observed practices into
   `docs/standards/<domain>/*.md` **with `applies_to` globs** (the globs wire each doc into the
   code map), extends naming rules from observed patterns, then runs
   `index rebuild` + `struct` + `sync`. Plus a `context-coverage` doctor check that reports
   source areas the map does not cover.
4. **The configurable commit gate.** `/commit` is the developer's final command before pushing
   upstream, so WHAT it checks and updates is decided per project during init: a late interview
   step writes `.agent/skills/commit/references/commit-checklist.md` from the developer's
   answers (a sensible default ships so commit works pre-customization), and the commit skill
   runs every checklist item and refuses to present the message until all pass or the developer
   explicitly waives them.
5. **The setup report** (added 2026-08-07). `init finish` writes `docs/setup-report.md` — a
   developer-facing explanation of everything configured (platforms, modules, domains, workflow,
   commit gate) and how agents will use the harness, with a "review this and request changes"
   framing; the init skill appends its discovery findings and presents the path as its last act.
6. **Migration-by-init** (replaces runbook execution as the default path). The init skill's
   inference explicitly mines EXISTING agent setups — `.pi/agent-docs/**`, `.claude/commands/`,
   `CLAUDE.md`/`AGENTS.md` files — as primary draft sources per phase; the developer runs
   `/harness-init` per project themselves and deletes old trees afterward (08's runbook remains
   the reference for what maps where and what is safe to delete).
7. **Distribution-lite.** `src/cli.ts` gets a `#!/usr/bin/env bun` shebang and the package is
   globally linkable (`bun link` → a `harness` command on PATH, running from this source tree);
   `harness/README.md` documents install + the command surface. Compiled binaries stay deferred.
8. **CLI rename** (developer request): the terminal entry point is `harness install
   [--template]` (formerly `init scaffold`); `harness init` keeps only the skill-plumbing subs
   (write-phase / status / finish).
9. **Live-test fixes from the first real init (maprios, 2026-08-07):**
   a. **Verify-then-adopt is the mining default** — existing agent docs are drafts to verify
      against the actual code (claims classified verified/corrected/dropped, drift reported),
      never facts to migrate. The code is usually newer than the docs.
   b. **Trusted-context opening question** — before any inference, init asks which documents
      the developer KNOWS are current/authoritative (and what to distrust); those anchor all
      verification.
   c. **Subagent fan-out is the discovery default** — one subagent per standards domain where
      the platform supports it (Claude Task tool / OMP subagents), main agent reconciles and
      writes; serial fallback otherwise. Post-init follow-ups land in tasks inbox.
   d. **`harness install` bootstraps a minimal bridge** — a fresh project has no manifest, so
      sync can't run, so OMP/Claude saw no `/init` at all. Install now writes the skills
      symlinks, the `/init`+`/harness-init` shims, `CLAUDE.md`, the OMP double-load guard, and
      the gitignore block, all recorded in the sync-manifest so the first full sync adopts
      them hash-clean (and prunes inactive platforms' pieces).

## Design Decisions

- **D09-1 Command shims are one-per-skill, both platforms**, generated by the existing adapters
  (no sync-engine changes — they are ordinary planned files). Claude: `.claude/commands/<name>.md`
  (frontmatter `description` from the skill + body). OMP: `.omp/prompts/<name>.md` (OMP prompts
  parse `description` frontmatter and support `$ARGUMENTS`; OMP `commands/` files are raw-content
  and stay unused). Every skill on disk with a non-empty `description` gets a shim.
- **D09-2 The init rename**: the Claude shim for the `init` skill is `harness-init.md` → invoked
  as `/harness-init` (builtin `/init` collision); the OMP shim keeps `init.md` → `/init`. All
  other shims use the skill name verbatim on both platforms.
- **D09-3 harness-guide.md is generated once** by `init finish` (template + substitutions), then
  developer/agent-maintained (NOT regenerated by sync — it may accumulate project-specific
  guidance; doctor does not budget it). `AGENTS.post-init.md` gains a pointer line.
- **D09-4 Discovery is a skill phase, not a CLI phase.** The CLI's 10-phase ledger is untouched
  (no migration for already-initialized projects). The skill runs discovery between
  `write-phase 9` and `finish`; its outputs are ordinary standards-file writes + the existing
  mechanical commands. Re-init "update" mode may run discovery alone.
- **D09-5 context-coverage** is info-severity: it surfaces map holes; it never fails a build.
- **D09-6 The commit checklist is a per-project reference file**, not a manifest field:
  `.agent/skills/commit/references/commit-checklist.md`. References are content, skills are
  routers — this is the sanctioned customization point, it survives `harness sync` (skills live
  in `.agent/`, the source of truth), and it holds both runnable commands and prose validations.
  A default ships in the embedded template; the init interview rewrites it.
- **D09-7 Interview ordering is foundational-first and binding.** Phases already flow
  identity → purpose → domains → stack → processes → deps → workflow → naming → mission; the
  commit-gate step runs AFTER phase 9 because its sensible defaults depend on earlier answers
  (dev commands from phase 5, commit_mode + modules from phase 7). The skill must not reorder
  phases — later questions assume earlier answers exist.

## Step 2: harness-guide template `[agent]`

- [ ] Create `src/templates/agent/harness-guide.md` (≤120 lines)

Full content (placeholders `{{PROJECT}}`, `{{DOMAINS}}`, `{{MODULES_ON}}`, `{{MODULES_OFF}}`):

Sections, in order:
1. `# Agent Harness Guide — {{PROJECT}}` + one-line purpose ("read this before editing any
   part of `.agent/`").
2. **Layout** — the `.agent/` tree annotated with GENERATED vs AUTHORED vs LEARNED per path
   (manifest/AGENTS.md/guide = authored-once; standards/preferences/anti-patterns/naming =
   learned; context-rules.yaml, index.yml, directory-structure.md, state.md, .sync-manifest.json,
   bridges = generated — list the generating command for each).
3. **Where knowledge goes** — the routing table (proposal §10): corrected mistake →
   `anti-patterns.md` (AP-NNN, append-only) · style/API pattern seen ≥2× → `preferences.md`
   (P-NNN grammar) · naming pattern → `naming-conventions.md` rules block + `harness struct` ·
   architectural decision → `decisions/ADR-NNN.md` · coding practice for an area →
   `docs/standards/<domain>/<topic>.md` **with `applies_to` globs** · dependency insight →
   `docs/research/` · env var → `env.manifest.md` · session narrative → `harness log append`.
4. **The code map** — how linking works: `applies_to` frontmatter + naming-rule `scope` globs →
   compiled by `harness sync` into `context-rules.yaml` → queried via
   `harness context --for "<task>"` (auto-injected in OMP via instructions). Rule of thumb: **a
   standards file without `applies_to` is invisible to the map** — always set it.
5. **Active configuration** — domains: {{DOMAINS}}; modules on: {{MODULES_ON}}; modules off:
   {{MODULES_OFF}}; budgets come from `manifest.json#doctor.budgets`.
6. **Editing rules** — never edit generated files (list them; run the generating command
   instead); run `harness sync` after any standards/skills change; `harness doctor` tells you
   what is stale; cascade changes (renames, deletions) must be checked against dependents.

SKILL.md insertion (contract, exact wording implementer's choice within budget):

```
## Discovery pass (after phase 9, before finish)

Read `references/discovery.md`. Sweep the ENTIRE codebase domain by domain and write what you
observe into the harness — this is what makes future agents follow existing practice. Present
a summary of every file you created or extended before moving on.
```

`references/discovery.md` full content covers, per domain in `standards_domains`:
1. **Sample deeply, not exhaustively**: read the 5–10 most representative files per area
   (entry points, the largest module, the newest module, one test) plus any lint/format configs.
2. **Extract practices worth recording** — the bar: would an agent writing new code here get it
   wrong without this? (error-handling shape, module layout, import conventions, API patterns,
   test structure, fixture patterns). Skip anything a linter already enforces.
3. **Write** `docs/standards/<domain>/<topic>.md` — one topic per file, ≤60 lines, with
   `applies_to: ["<globs>"]` frontmatter scoped to where the practice applies. No applies_to →
   the map cannot inject it (harness-guide.md rule).
4. **Naming**: verify every observed file-naming pattern has a rule in the naming-conventions
   block; add missing rules (id/pattern/scope/description/examples).
5. **Mechanical close**: `harness index rebuild` → `harness struct` → `harness sync` →
   `harness doctor` (fix findings) → spot-check the map with 2–3
   `harness context --for "<real task phrasing>"` queries and confirm the right docs return.
6. **Report**: files written, rules added, map coverage gaps you chose to leave (with why).

**Default `commit-checklist.md`** (full content, ≤60 lines) — two sections:

1. `## Must pass` (blocking — each line `- [ ] <check>` with the command where runnable):
   `harness doctor` exits 0 · project build passes (command from
   `.agent/docs/product/dev-processes.md`) · project tests pass (same source) ·
   `harness struct --check` clean · no unintended files staged (review `git status`).
2. `## Must be current` (updates performed, not just checked): today's session-log entry filled ·
   `docs/tasks.md` reflects finished work · `harness struct` run if files were added ·
   `harness state` regenerated · (modules.roadmap) milestones ticked · (modules.decisions)
   new architectural decisions captured as ADRs.

Header note: "Customized during `harness init`'s commit-gate step; edit freely — the commit
skill runs every line, every time."

**Commit skill Gate step** (contract): load `references/commit-checklist.md`; execute every
"Must pass" item (run the commands, report each ✅/🔴) and perform every "Must be current"
update; any failure → present the failures and STOP — do not present the commit message unless
the developer explicitly waives the failing items (record a waiver line in today's session-log
entry). This replaces/absorbs the current step-5 document-update list (fold those items into
the default checklist rather than duplicating them).

**Init interview step** (in phases.md, after Phase 9; skill-driven, no CLI write-phase — the
skill writes the reference file directly):

```
## Commit gate (after phase 9)

/commit is the final command before code goes upstream. Show the developer the default
checklist (templates ship it), pre-filled with THIS project's build/test commands from phase 5
and module-gated items from phase 7. Ask: what else must be checked or updated on every
commit? What should be removed? Write the result to
.agent/skills/commit/references/commit-checklist.md.
```

Test additions (templates.test.ts): the default checklist exists, ≤60 lines, contains both
section headings; the commit SKILL.md contains "commit-checklist.md" and stays ≤150 lines.

## Step 6: Doctor check `context-coverage` `[dev]`

- [ ] Create `src/checks/contextCoverage.ts` + test; register in `src/checks/index.ts`; run tests

Contract: id `context-coverage` · severity `info` · appliesWhen `ctx.read(P.contextRules) !== null`:

```
// 1. rules = yaml-parse context-rules.yaml → all `when` globs (parse failure → single info
//    "context-rules.yaml unparseable", hint "harness sync").
// 2. Source files = walk(root) minus .agent/**, bridge dirs (.omp/, .claude/), dotfiles at
//    root, and non-source extensions (keep: ts,tsx,js,jsx,py,rs,go,java,rb,swift,kt,c,h,cpp).
// 3. Group by top-level directory (files at root → skip). For each dir with ≥5 source files:
//    covered iff ANY file matches ANY rule glob (globMatch). Uncovered → one finding:
//    `<dir>/ (<n> source files) matches no context rule` , hint
//    "add applies_to globs to a standards doc covering it (see docs/harness-guide.md)".
// Edge cases: no rules at all + ≥1 source dir → finding per dir; a dir covered only by the
//   naming rule counts as covered (any rule counts).
```

Test: synced fixture → `src/` is covered by the naming rule scopes → ✅ line. Seed
`services/` with 5 `.ts` files (committed or not — walk is disk-based) → exactly one info naming
`services/`. Sub-5-file dirs stay silent.
